# 作業パターンの記録項目

`refinery-review-session` が作成し、`refinery-propose-improvements` が検討に使う共通の記録項目。
各作業にレポート内で一意のID（例: `W01`）を付ける。複数レポートでは
「レポートパスまたはセッションID + 作業ID」で参照する。表でも段落でもよい。

| 項目 | 残す根拠 |
| --- | --- |
| 目的・きっかけ | 解決した課題、作業を必要とした依頼や条件、対象リポジトリ／利用場面 |
| 入力・出力 | 入力の種類、変わる引数、生成物や状態変更、成功を確認した方法 |
| 手順と判断 | 成果までの主要手順、機械的に決まる処理、文脈に応じた判断や人の確認 |
| 前提と副作用 | 観測した依存ツール・環境・権限、外部アクセスや書込み、失敗・再実行時の挙動 |
| 観測回数と負担 | 独立した作業の回数と根拠位置、同じ作業内の再試行・待機、手戻りや利用者の訂正 |
| 既存の手段・指示 | 使用・参照したSkill、CLI、スクリプト、AGENTS.md等と当時確認できた役割。規約の欠落、矛盾、遵守されなかった指示があれば区別する |
| 再利用の仮説と限界 | 次回も共通しそうな部分、今回固有の部分、未確認の頻度や前提、判断に足りない情報 |
| 根拠位置 | 元ログの行番号またはターン／呼び出しID。成功例と重要な失敗例の位置 |

観測した値と推定を区別する。不明な項目は「不明／記録なし」とし、後から埋めるために
コマンドを再実行しない。所要時間や費用は記録がある場合だけ測定範囲付きで残す。
再試行や同じ履歴の転載を独立した利用回数に数えない。1回だけでも候補の根拠にはなるが、
将来の利用頻度が確認されたことにはしない。

規約は適用範囲と、いつ必要だったかを残す。特定セッションだけの依頼を恒久的な規約と
決め付けず、既存のAGENTS.mdに書かれていたのに守られなかった場合も明記する。
秘密値や個人情報は引数の役割が分かるプレースホルダーに置換し、再利用に不要な生データは載せない。
